## Outcome

**Accepted with Documented Limitations** (recommended on 2026-10-28, after #836 fixed finding 2; it was Changes Required).

The engine does what 8.2 asks, and the tests prove it. Ports keep a version history. Links declare `accepts`. A deprecation date sends one Teams notice and is enforced after it passes. Two problems were found. Finding 1 is fixed in #817 and finding 2 in #836, so nothing blocking remains:

- **Security (finding 1, fixed).** A security gap in publishing data products (BQ-013), found in this review, is fixed by #817 (quality PASS 9.0 at ac58d712). The fix applies once a platform admin runs **Platform > Settings > Finish or repair** to redeploy UDF_Platform.
- **Widening `accepts` can't reach the catalog (finding 2, fixed).** Fixed by #836 (quality PASS 9.1 at 81e4c03e): publishing re-sends each link whose file differs from the catalog, New link keeps the file's `accepts` and `columns`, and the block message says to edit the link's file and promote. Before #836: when a consumer's `accepts` blocks the producer, the block message tells the consumer to "widen accepts in the link". Editing the link file doesn't reach the catalog, so the producer stays blocked. The app has no screen to change an existing link. Adding the link again with the same alias from **New link** clears `accepts` in the file and in the catalog, so the link then accepts any version.

All of 8.2 is engine-only. There is no screen for `accepts`, link columns or port history, and `product_history` has no engine RPC (finding 4). The deprecation date was already editable in the product dialog.

Recommended by: Engineering quality review. Decided by (product owner): Chris, "I approve all of these move these forward" on 2026-10-28 (project message cmsg_018T4o2pQdpbLBNhHpgVNNGpFeQHvbSrE9FwPZyTzr8ao4), on the acceptance batch: Accepted with Documented Limitations.

## Acceptance criteria

The criteria come from FD-127 / 8.2 (`docs/scale-and-operations-plan.md:186`): "Ports carry a schema version and history in the catalog; consumers declare a compatible range; deprecation sets a date, notifies consumers through the 9.1 alert path and is enforced after it."

| # | Criterion | Result | Evidence |
| ---: | --- | --- | --- |
| 1 | Ports carry a schema version and history in the catalog | Met (engine) | New table `catalog.port_version` (`central/core.py` `_CATALOG`). `register_product` adds one row per port per environment when the version or columns change (`_record_port_version`, `core.py:759`). Re-publishing the same thing adds no row. `product_history` (`core.py:773`) returns rows newest first, and is exposed as a UDF (`central/udf.py`). Ids end in a random part, so two publishes in the same microsecond keep both rows. Tests: `test_history_gets_a_row_only_when_the_version_or_columns_change`, `test_two_publishes_in_the_same_microsecond_keep_both_history_rows`. Nothing in the app reads the history (finding 4). |
| 2 | Consumers declare a compatible range | Met in the engine after #836 (widening was broken, finding 2) | `accepts = "2" / "2-3" / "2+"` on a link (`meta/mesh.py:42-67`, the `validate` save gate). The catalog keeps it, with the link's `[columns]`, in two new `catalog.link` columns (`register_link`, `core.py:1069`). A new link saved without `accepts` gets the product's current version (`central/service.py:1165`, `_current_version`). Older links keep reading any version. `breaking_changes` (`mesh.py:428`) blocks a raised version that a reader's `accepts` leaves out, and a reader that listed its columns is only broken by a change to one of them. The consumer can widen `accepts` only by calling `mesh_save_link` again with it. The UI's **New link** never sends it (`app/ui/mesh.js:410`), and editing the file isn't synced (probe below). |
| 3 | Deprecation sets a date, notifies consumers (8.2 says through the 9.1 alert path) and is enforced after it | Met, with a different notice path | The date comes from the product's `deprecated_on` (already in the product dialog, `app/ui/mesh.js:312`). The first publish as deprecated, or one with a new date, sends one `product.deprecated` event per date (`governance_notices.py:125`, deduplicated on `product.deprecated:<id>:<date>`). It goes to the platform's Teams routes (`workloads/platform_notify.py`), not the 9.1 incident path. 9.1 moved to another program (`scale-and-operations-plan.md:148`), and the plan's own status line says "a Teams notice". A notice that fails never fails the publish. Enforcement: after the date, `register_link` refuses new links (`core.py:1088`), and `_deprecation_gate` (`meta_service.py:783`, run in both promote check and promote) blocks the consumer's promote. Runs aren't stopped, by design. Tests: `test_a_new_link_is_refused_once_the_deprecation_date_comes`, `test_a_link_to_a_product_past_its_deprecation_date_blocks_the_consumers_promote`, `test_deprecating_a_product_tells_its_readers_once_and_a_failed_notice_doesnt_fail_the_publish`, `test_a_prod_deprecation_is_told_once_not_again_as_a_product_change`. Who may publish the date is covered by finding 1 (fixed in #817). |
