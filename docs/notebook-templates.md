# Notebook templates for Silver and Gold (Preview)

KratosForge ships **enterprise notebook templates** for the three notebooks every medallion platform needs, for
Fabric, Databricks and Snowflake. Each one already follows the standards below, so the quickest way to build a
table is also the supportable one. A domain builds with a template, and when the notebook still conforms to it,
hands it to the enterprise to run and maintain. Anything else stays the domain's own work.

| Template | Kind | What it builds |
| --- | --- | --- |
| Silver table | `silver` | Cleans a Bronze table to a contract, adds surrogate keys from the key table, upserts into Silver |
| Gold dimension, Type 1 | `gold_dim_type1` | Current values only, keyed by the Silver key, with an Unknown member |
| Gold dimension, Type 2 | `gold_dim_type2` | History with valid from and to dates, version and durable keys, an Unknown member |
| Gold fact | `gold_fact` | A declared grain, dimension keys and numeric measures only, misses to the Unknown member |

The Native skin runs Fabric notebooks, so it uses the Fabric templates. The Learn module **LM-36 Enterprise
notebook templates** walks through them with a hands-on exercise.

## Use a template

```
fabric-desktop templates list
fabric-desktop templates new fabric silver nb_crm_to_silver_customers.ipynb
```

Open the copy and fill in **only the Parameters cell**: table names, the business key, the columns and their
types, the measures. Leave every cell that starts with `# kratosforge:standard` as it is. Add Markdown cells
for notes whenever you like. Then import the notebook into the platform as usual: Fabric and Databricks import
`.ipynb` files, and so do Snowflake Notebooks.

Parameters are checked before any SQL is built: table and column names must be plain names and types must be
known types, because pipelines and jobs can override parameters.

## The standards in each template

**All templates**

- One lakehouse per layer, schema-enabled, on Fabric (`LH_Bronze`, `LH_Silver`, `LH_Gold`, keys in `LH_Keys`);
  one Unity Catalog catalog per layer on Databricks; one database per layer on Snowflake.
- Writes are `MERGE` upserts that update a row only when its hash changed. No template overwrites a table.
- Every row carries `_run_id` and `_loaded_at`; Silver and dimensions carry a row hash.
- A check cell at the end stops the run when a rule is broken (duplicate keys, overlapping versions, a broken
  grain, a key missing from its dimension).
- The Fabric and Databricks templates pass the [notebook best-practice rules](notebook-best-practices.md).
  The Snowflake ones run SQL through Snowpark's `collect()`, which NB003 flags; every statement there returns
  one summary row or at most five rows.

**Silver: surrogate keys that fit each platform**

Every business key gets its surrogate key from one key table per business key (`<name>_sk`, `<name>_bk`,
`create_date`), so the same business key gets the same key from every source, and a rebuild never renumbers it.

| Platform | Key table | How a new key is issued |
| --- | --- | --- |
| Fabric | `LH_Keys.sk.<name>`, `INT` | Lakehouse Delta tables have no identity columns, so an insert-only `MERGE` issues `MAX(key) + ROW_NUMBER()`, retried on a concurrent write |
| Databricks | `keys.sk.<name>`, `BIGINT GENERATED BY DEFAULT AS IDENTITY` | The identity column; the `MERGE` only adds business keys. `BY DEFAULT` lets the keys admin seed `-1` |
| Snowflake | `KEYS.SK.<NAME>`, `NUMBER(10,0) DEFAULT <NAME>_SEQ.NEXTVAL` | A sequence; the `MERGE` only adds business keys. Snowflake doesn't enforce unique constraints, so the `MERGE` keeps business keys unique |

A keys admin creates each key table once and seeds the Unknown member (`-1`, business key `UNKNOWN`); the first
cell of the Silver template has the statements. Composite business keys are joined with `||`, with any `|`
inside a part escaped, the same way the metadata framework does it. Silver also:

- keeps only the columns in its contract, each cast to its type (no `SELECT *`);
- trims text, turns blank text into NULL and lower-cases the columns you name;
- sends rows with no business key to `<target>_quarantine` with a reason;
- keeps the newest row per business key, reads incrementally with `watermark >=` the newest one stored (so rows
  that share the last timestamp aren't lost) and never lets an older row overwrite a newer one.

**Gold dimensions**

- Always have an **Unknown member**, `-1`, with `Unknown` in text columns, so a fact whose dimension row is
  missing still joins.
- Keep the business key as an attribute, and hold no measures.
- **Type 1** uses the Silver key as the dimension key, so facts never need re-keying.
- **Type 2** has a version key (`<name>_sk`, which facts use) and a durable key (`<name>_dk`, the Silver key).
  `valid_from` is inclusive and `valid_to` exclusive; the first version starts at `1900-01-01` and the current
  one ends at `9999-12-31`. One `MERGE` closes changed versions and adds the new ones, so a failed run never
  leaves a row without a current version. `type1_columns` corrections overwrite every version. The version key
  comes from `MAX + ROW_NUMBER()` on Fabric, an identity column on Databricks and a sequence on Snowflake.
- Rows deleted in Silver stay in the dimension, because facts may still point at them.

**Gold facts**

- **Declared grain.** `grain` says in words what one row is; `grain_columns` are the dimension keys that make a
  row unique. The run stops if two source rows share a grain.
- **No degenerate or descriptive fields.** Only dimension keys (named `<name>_sk`) and numeric measures. An
  order number, status, name, code or flag goes in a dimension (such as `dim_order`) and the fact keeps that
  dimension's key. The rules cell refuses a text measure, a measure named like an identifier
  (`_id`, `_number`, `_code`, `_status`, ...) and an existing table with any other column.
- Each key is looked up by its Silver key; Type 2 dimensions take the version valid on the fact's date. A miss
  gets `-1`, never NULL, and the share of misses per dimension is reported.
- Rows whose grain key is `-1` can't be placed, so they go to `<target>_quarantine`.
- Each run re-reads `lookback_days` of Silver, so rows that went to `-1` pick up a late dimension row.

## Enterprise or domain: who supports a notebook

Every template carries handover markup:

| Cells | Marked | Owned by |
| --- | --- | --- |
| Parameters | `# kratosforge:parameters template=... platform=... version=...`, and the `parameters` tag | The domain: the values, and what the data means |
| Every other code cell | `# kratosforge:standard template=... platform=... version=... cell=...` | The enterprise: it maintains, fixes and upgrades them |
| Markdown | none | Anyone |

The marker is the first line of the cell, so it survives an import into any platform. The notebook's metadata
(`kratosforge.template`, `kratosforge.support`, `kratosforge.handover`) records the same, plus the handover state.

A notebook **conforms** while its standard cells are unchanged and in their order, it has no code cells the template doesn't have,
and its Parameters cell only sets values. Then the enterprise can support it. Editing a standard cell, adding a
code cell or putting code in the Parameters cell makes it **domain-owned**: it still runs, but the domain
supports it.

```
fabric-desktop templates check nb_crm_to_silver_customers.ipynb
fabric-desktop templates handover nb_crm_to_silver_customers.ipynb --domain Sales --owner ana@contoso.com
fabric-desktop templates accept nb_crm_to_silver_customers.ipynb --by "Data platform team"
```

- `check` names the template and version and lists every change that makes the notebook domain-owned. It exits
  with 1 when the notebook doesn't conform, so a CI job or a promote step can use it.
- `handover` is refused unless the notebook conforms. It marks the notebook's handover as requested and writes
  `<notebook>.handover.json` next to it: the template, version, parameter values, domain, owner, a hash of the
  cells and the split of responsibilities. The enterprise keeps that record.
- `accept` is for the enterprise, with the handover record it reviewed (`--record`, by default
  `<notebook>.handover.json`). It is refused unless the notebook's code and every parameter value are exactly
  what the record describes, so a notebook repointed at another table after the handover isn't accepted. It
  marks the notebook as enterprise-managed.
- The handover state in a notebook is plain metadata, not a signature: anyone who can edit the file can change
  it. The enterprise's own copy of the handover record, kept on its side, is the source of truth for what it
  supports; compare a notebook's code with the record's `code_sha256` and parameters, as `accept` does.
- When a handed-over notebook changes later, `check` warns that it left the enterprise's support.

`standards.json` keeps the hash of every standard cell of every released version, so a notebook built from an
older version still conforms, and `check` says when a newer version is out.

Need logic the template doesn't have? Derive the column in Silver, or ask the enterprise to add it to the
template, so every domain gets it. Changing a standard cell in one notebook takes that notebook out of the
enterprise's support.

## What this doesn't do yet

- There is no page in the app to pick a template; that needs a design first. Use the command, or copy a
  file from `sidecar/fabric_desktop/notebook_templates/`.
- The Fabric templates were run end to end on Spark 3.5 with Delta 3.2, and the Databricks dimension Type 1
  and fact templates on Spark 4 with Delta 4. Identity columns only exist on Databricks itself, and the
  Snowflake templates need a Snowflake account, so those haven't been run yet. All of them are Preview until
  they have run on each platform.
- On Fabric, two Silver runs adding new business keys to the same key table at the same moment rely on Delta's
  conflict detection and the retry to never issue one key twice; the final check covers the Silver table, not
  the key table.
- Templates don't handle rows deleted at the source, and re-keying facts older than the lookback window needs
  a `full_reload` run.

## For template maintainers

The templates live in `sidecar/fabric_desktop/notebook_templates/<platform>/<kind>.ipynb`. To change a standard
cell, raise `VERSION` in `notebook_templates/__init__.py` and the version in every cell marker and in the
notebook metadata, then run `python -c "from fabric_desktop.notebook_templates import record_version; record_version()"`
to add the new version's hashes to `standards.json`. A released version's hashes never change, so notebooks built
from it keep conforming. `tests/test_notebook_templates.py` checks every template against its hashes, the notebook
rules and the fact rules.
