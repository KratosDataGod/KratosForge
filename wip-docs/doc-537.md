# Mutation testing, batch 537

A re-score of `databricks_variant.py` on today's `main`. It is Databricks' VARIANT on this PC: `parse_json` and `try_parse_json`, `variant_get` and `try_variant_get` with their paths and casts, `variant_explode` and `to_variant_object`, kept as JSON text in DuckDB. Batch 28 left it at **95.3%** on point mutants, batch 36 at **78.9%** on boundary mutants, and batch 233 at **94.7%** (kinds all), with 8 equivalent mutants. Since batch 233, #3247 (the SQL text fuzzing) made `parse_json` refuse a string or key that holds half of a UTF-16 pair on its own (`\ud800` to `\udfff`), by name, before it crashed sorting keys or handing the text to DuckDB. Its tests are in `test_snowflake_databricks_sql_fuzz.py`, which isn't in this module's set, so the sample is new in part.

The run was at `main` be5ef815c (2026-11-28), with `sidecar/tools/mutate.py` and the method of earlier batches (sample cap 150, seed 7, `--kinds all`), on DuckDB 1.5.6. The per-mutant timeout was raised from 120 to 600 seconds by a wrapper that sets `mutate.TIMEOUT`, with the tool unchanged; no mutant's run timed out. Each pytest session got a fresh temporary folder, and each test set was run with `-x`. The first "before" run stopped part way with no result, so it was run again from the start; the figures are from the second run. The module now has 280 mutants, so 150 were sampled. The test set was batch 233's after set: test_databricks_variant_edges, test_databricks_coverage, test_databricks_variant_mutation, test_boundary_mutation and test_databricks_variant_rescore. Test files were given as paths relative to `sidecar/`, and they first passed once on the unmutated copy. Three tests in `test_databricks_coverage.py` read `docs/` (`test_what_the_docs_say_runs_still_runs`, `test_the_docs_page_is_up_to_date`, `test_the_docs_link_the_list`), so they were deselected, as in batch 233.

Before the "after" run, the new tests passed in a copy of `sidecar/` on its own and against the module as `ast.unparse` writes it. They also pass on DuckDB 2.0.0.

### What the survivors were, and the tests that now kill them

- **databricks_variant.py**:
  - A string or key that holds half of a UTF-16 pair on its own is refused by name ("half of a UTF-16 pair"), by `parse_json` and `try_parse_json` alike, wherever it sits: the value itself, a list in a list, an object's key, or an object in an object. A whole pair (an emoji) and other `\u` text still read. Five mutants of `_lone_surrogate`'s walk and of the `raise` in `_load` dropped this.
  - `variant_get` and `try_variant_get` name themselves when they are given a value that isn't a VARIANT (`[DATATYPE_MISMATCH] try_variant_get() takes a VARIANT, not VARCHAR`).
  - A whole number one digit too wide for a scale-0 decimal doesn't fit: 123 as `decimal(2,0)` is NULL from `try_variant_get` and `INVALID_VARIANT_CAST` from `variant_get`, while 12 fits. The mutant counted one digit fewer before the point.
  - → `test_databricks_variant_mutation_b.py`.
