# Mutation testing, batch 223

One module, run uncapped: every one of its mutants, not a sample of 150.
- T-SQL on the local engine: a T-SQL script read with sqlglot and run as DuckDB SQL (`localdata/tsql.py`).

Batch 3 sampled 150 of this module's mutants then, 694 in all (100% before, no change needed), and batch 155 ran its 55 boundary mutants (30.9% before, 81.8% after). The module has 2,345 mutants now. This run made all of them: `--cap 100000 --seed 7 --kinds all`, so 2,345 of 2,345 (2,271 point + 74 boundary), the boundary mutants (`<` to `<=`, `>` to `>=`) counted with the earlier kinds.

The run was at `main` 293fb38da (2026-11-23), merged into the branch first (8957d26c9), with `sidecar/tools/mutate.py` as it is since #2902. Line numbers below are the module's at that commit. Test files were given as paths relative to `sidecar/`, and each was checked to exist before the run. The tests first passed once on the unmutated copy. Each pytest run had a temporary folder of its own, made fresh by a local plugin and removed when the run ended, so another run's leftover files could not fail a mutant and no run left files behind. Three "killed" mutants picked at random (75, 163 and 32) were run again by hand, and each failed a real test: 75 (a return value dropped, line 1182) makes the module raise a TypeError in test_everyday_tsql_runs_and_gives_tsql_answers, 163 (a negated condition, line 2033) lets `2 IN ('1.5')` run where T-SQL's conversion error is expected, and 32 (a negated condition, line 596) refuses everyday T-SQL.

The run used batch 3's and batch 155's test files (test_local_tsql, test_local_tsql_more_edges, test_local_tsql_boundary, test_sql_lambdas, test_tsql_loud_gaps) and the module's other focused files: test_tsql_tables_mutation, test_tsql_format_mutation, test_tsql_routines_mutation, test_tsql_hints_mutation, test_tsql_arithmetic, test_tsql_decimals, test_tsql_strings, test_tsql_dates and test_tsql_text_comparisons. The set runs in about 30 seconds. Three tests in `test_tsql_loud_gaps.py` read `docs/`, so they were left out with `--deselect`, as in batches 3 and 155. The other 28 T-SQL test files were too slow to run against every mutant. Instead each survivor of the main run was run, one at a time, against those files in five groups, with the same fresh-folder plugin; a group counted as a kill only when pytest itself reported a failed test (exit 1), never on a timeout or a collection error, and each group was first checked to pass on the unmutated module. Those groups were test_tsql_changes, test_tsql_clone, test_tsql_clone_mutation, test_tsql_collation, test_tsql_contract, test_tsql_cov2, test_tsql_ctes and test_localdata_tsql_ctes_mutation; test_tsql_data_types, test_tsql_error_numbers, test_tsql_errors, test_tsql_formatting, test_tsql_fuzz, test_tsql_hints and test_tsql_json; test_tsql_loading, test_tsql_merge_edges, test_tsql_names, test_tsql_national_text, test_tsql_routines and test_tsql_scripts; test_tsql_security_settings, test_tsql_table_forms, test_tsql_tables, test_tsql_time_travel, test_tsql_transactions and test_tsql_windows; and test_tsql_wide_and_long. They killed 419 of the 777 survivors. The "after" score counts those, the main run's kills and the after runs' kills.

Before the "after" run, its tests were run in a copy of `sidecar/` on its own and against the module as `ast.unparse` writes it, as in batch 11. They passed both ways (953 passed and 6 xfailed each time, on DuckDB 1.5.6, and on 2.0.0 in the copy), so no run below can score a false 100%. No `-k` filter was used. The after run was made twice with `--only`: once on the 440 survivors no group had killed, and again on the 183 still left, with the new test file as it was at the end.

Six mutants timed out: 954, 1333 and 1794 in the main run, and 1785, 1786 and 2185 in the after runs, under the new tests. Each was then run again on its own with a longer limit, and each really hangs, so each counts as killed:
- 954 (line 1821, `i += 1` to `i += 0` in `_like_regex`) and 1794 (line 148, the same change in `_left_open`'s scan): the module's own call on a short input (`_like_regex('ab')`, `_left_open('SELECT 1')`) was still running after 100 seconds, where the original answers at once.
- 1333 (line 1859, `k += 1` to `k += 0` in `_like_range`): under a 3 GB memory limit it stops with a MemoryError. The scan never moves on and keeps adding to its result.
- 1785 (line 122, `i + 2` to `i - 2` after a `/*` inside a comment) and 1786 (line 126, `i += 1` to `i += 0` inside a comment): `_left_open('/* a /* b */ c */ SELECT 1')` was still running after 120 seconds on each, where the original answers None at once. The scan steps back onto the same `/*`, or never moves.
- 2185 (line 330, `others[1:]` to `others[0:]` in an UPDATE's FROM): `UPDATE x SET a = 1 FROM dbo.t AS x JOIN dbo.u AS y ON x.a = y.a` was still being translated after 400 seconds. The FROM's first table is joined to itself.

One more process is worth naming. During the main run, the box ran out of memory once (mutant 500, a negated condition at line 1816 in `_like_regex`, took about 13 GB). The kills logged near it were checked again: 33 of the 34 between mutants 485 and 520 fail named tests when run by hand, and 500 itself stops with a MemoryError on `'[a]b'` and an UnboundLocalError on `'ab'`. So it is a real kill.

### Bugs found

Three, each pinned with `xfail(strict=True)` in `test_local_tsql_uncapped.py`, so a fix turns the test into an XPASS that fails until the mark is removed:
- **ALL and ANY against a subquery ignore T-SQL's trailing-space rule.** sqlglot gives the All/Any node a Select, not a Subquery, so the padded-comparison branch (line 1915) never matches. `'a ' > ALL (SELECT s FROM dbo.t)` over a row `'a'` returns a row locally where T-SQL returns none, and `'a ' = ALL (...)` returns none where T-SQL returns one. Found from mutant 974. → `test_a_comparison_against_all_of_a_subquery_ignores_trailing_spaces_as_t_sql_does`.
- **SELECT DISTINCT * and a UNION of SELECT * over a text column get no grouping note (WR-210).** The typed copy is qualified with `expand_stars=False` (line 1068), so the star stays a Star whose type isn't text, where `SELECT DISTINCT s, n` gets the note. Found from mutant 1601. → `test_distinct_over_a_star_with_a_text_column_has_the_grouping_note` (two cases).
- **A length just below a bigint gives the wrong error.** At 293fb38da a negative literal reached the bigint range check through a float, so `LEFT('abc', -9223372036854775809)` rounded to -2^63, passed, and gave LEFT's "Invalid length" error, where T-SQL fails to convert the value to a bigint. On `main` since WR-247 (#3248), that statement and `LEFT('abc', -10000000000000000000)` (which batch 223's run answered correctly) stop with DuckDB's own "Failed to cast decimal value ... to type INT64" message. → `test_a_length_one_below_a_bigint_is_t_sqls_bigint_overflow` and `test_a_length_far_below_a_bigint_is_t_sqls_bigint_overflow`.

Three differences were seen but not pinned, because T-SQL's answer was not checked here: `CONVERT(VARCHAR(10), d, n)` with a style taken from a column ignores the style; a DATETIME2(7) turned into text shows 6 digits of the second; and `DATEPART(year, 5)` stops with a DuckDB error, where T-SQL reads 5 as a datetime.

After the runs, `main` 5473df2ee2 was merged (db08add98a). WR-238 and WR-247 (#3184, #3248) changed `tsql.py` since 293fb38da, and seven of the new tests failed on the merged module. They were updated. Three overflow tests now accept T-SQL's message whether it comes from the translation or from DuckDB when the SQL runs, since WR-247 moved some of those checks into the SQL. Three decimal tests expect the extra cast WR-247 adds (`CAST(CAST(x AS DECIMAL(38, 2)) * y AS DECIMAL(38, 4))`, and a second `CAST(... AS DECIMAL(38, 6))` around an AVG). They were not run again on the merged module.
