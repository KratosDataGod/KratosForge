# Security model

How KratosForge protects your sign-in, your data and your PC, what it trusts, and what is still open. This is the threat model for FD-102; the [enterprise backlog](https://github.com/KratosDataGod/KratosForge/blob/main/docs/product/enterprise-backlog.md) and the [hardening backlog](hardening/backlog.md) track the open items. It describes `main` as of 2026-10-18 (a346145); the [hardening audit](hardening/README.md) checked it at 1248ccd and its fixes are reflected here. Its claims were checked against the code again at d0747a6 (2026-10-28, PB-010). The [security evidence pack](evidence-pack.md) collects this page with the rest of what a reviewer needs.

## What it protects

| Asset | Where it lives | Why it matters |
| --- | --- | --- |
| Your Microsoft sign-in (refresh and access tokens for Fabric, OneLake, Power BI, Graph, and Azure SQL and Kusto when those Preview features are used) | `%LOCALAPPDATA%\FabricDesktop\msal_cache.bin`, encrypted with Windows DPAPI for your Windows account; with Windows sign-in, the Windows broker holds the primary token | Anyone holding them can act as you in Fabric |
| The Fabric view's sign-in cookies | `%LOCALAPPDATA%\FabricDesktop`, encrypted with Windows DPAPI | Same as above, for Fabric's web pages |
| Teams webhook addresses (the alert address and each platform notice route's) | The engine's `settings.json`, encrypted with Windows DPAPI for your Windows account; an address saved in the clear by an earlier version is encrypted the next time it's read. Copies made before that (an older copy of `settings.json`, a synced or copied profile) aren't found or cleaned; the app's own backups leave both out, so where that matters enter the address again and ask the channel's owner for a new webhook. One that can't be decrypted here (another account or PC) counts as not set: the Teams alert address asks for it again, and a platform notice route shows no address until it's entered again | Anyone holding one can post to that Teams channel |
| Data in OneLake | Your tenant | Writes, overwrites and deletes are hard to undo for other people |
| Data on the PC | Previews, proof sandboxes, notebook outputs, local tables under `%LOCALAPPDATA%\FabricDesktop` and project folders | May hold personal or confidential data |
| Answers to platform changes (`catalog.call`) | The platform's `SQL_Platform` database. Each change made through `call_once` keeps its answer, up to 1 MB, for 7 days, so a retried change gets the same answer instead of being made twice. An answer can include catalog data, such as a domain, product or request | Readable by anyone with SQL access to `SQL_Platform`, like the rest of the catalog |
| The app and its engine | `kratosforge.exe` wherever you saved it; engine under `%LOCALAPPDATA%\FabricDesktop\engine\<build>` | Code that runs as you |
| The headless agent's identity | A certificate path or managed identity named in `agent.toml`; secrets only in environment variables | Acts as a service principal in Fabric |

## Pieces and trust boundaries

```
 Webview (app/ui, HTML + JS)  --Tauri invoke-->  Shell (Rust, main.rs)  --stdin/stdout JSON lines-->  Engine (Python sidecar)
                                                    |                                                     |
                                       GitHub releases (updates)                           Fabric REST, OneLake, Entra ID
```

1. **Webview to shell.** The UI calls a fixed list of Rust commands (`rpc`, `update_app`, `open_link`, ...) under a [Content Security Policy](#content-security-policy). Each validates its input: build commits are 40 hex characters, links are https or mailto, docs pages use a character allowlist.
2. **Shell to engine.** One Python process started by the shell, talking JSON lines over its own stdin and stdout. Only methods in `server.METHODS` can be called. Notebook output can't forge a reply, because the engine moves Python's stdout away from the pipe.
3. **External AI tools to engine.** Only when a person turns on **Settings > Integrations**: an MCP server per tool (`fabric-desktop mcp --client <id>`) and, if switched on, a local HTTP API on `127.0.0.1` (port 47615 by default). The HTTP API answers only loopback addresses, requires a `Host` naming the loopback address and port (stopping DNS rebinding), refuses any request carrying an `Origin` (so no web page can call it), on Windows answers only programs running as your own Windows account (so on a shared PC or Remote Desktop server another person's program can't use it, even with a token), won't start while another account's program holds its port (IPv4 or IPv6; tools should use `127.0.0.1`, not `localhost`, which on Windows tries `::1` first), caps bodies at 1 MiB and rate-limits each tool. Each tool has a token stored only as its SHA-256 hash. Running code always asks the person first. The full model is in [AI integration security](product/ai-integration-security.md).
4. **VS Code to engine.** Only while **Let VS Code run notebooks** (Settings > Integrations > VS Code) is on: the engine listens on `127.0.0.1` on a port it picks. A window pairs only with a value from your data folder and your yes, then sends a token with every call (only its hash is kept); requests from a web page, or with a `Host` that isn't this PC's loopback address, are refused. `integrations_editors: false` in the policy ends every pairing ([Run cells from VS Code](vscode.md#run-cells-from-vs-code)).
5. **Links from another copy of the app.** The running app listens on `127.0.0.1`, on a port it picks, so a copy that Windows starts for a `kratosforge://` link can hand the link over and exit. A line without the random token from your data folder is dropped, and a link is only ever shown, never run. `register_link_scheme: false` stops Windows sending links to the app; the app then doesn't listen for links from other copies, and it removes the port file an earlier run wrote ([Links into KratosForge](vscode.md#links-into-kratosforge)).
6. **Engine to Microsoft.** HTTPS to Fabric, OneLake, Entra ID and, for Preview features that need them, Azure SQL (warehouse queries) and Kusto (warehouse monitoring), with your delegated token. A Databricks SQL warehouse (Preview) gets its own Databricks token from the Databricks CLI or a service principal. The agent uses a service principal or managed identity instead.
7. **Shell to GitHub.** Updates come from this repository's `stable` and `latest` (the Preview channel) releases.
8. **Notebook code.** Code in a notebook runs as you, with your tokens, by design: it is your code. A notebook from someone else is code from someone else, and that includes its shell commands (`!command`, `%sh`, and `%%sh`, `%%bash`, `%%cmd` or `%%powershell` cells), which run in this PC's shell. Treat it like a script you were sent. It is **not sandboxed**: it can read your files, including the token cache. The same goes for Python an external AI tool runs after you approve it: its process starts without the app's environment variables (it keeps only `PATH` and `PATHEXT`, the temp and home folders, locale, proxy and certificate settings, and the Windows system folder, shell and processor variables; proxy addresses lose any user name and password), but it still runs as you, so it can decrypt and use your token cache: the encryption stops copies of the file, not code running as you.

## Threats and what stops them

| Threat | Mitigation | State |
| --- | --- | --- |
| Script injected into the UI (from a table value, file name or notebook Markdown) calls engine methods | Every value is put in the page as text (`h()`, `esc()` with quotes escaped since PR #51). A Content Security Policy is the second layer: only the app's own script files run, so injected markup can't run script (HD-020, [below](#content-security-policy)) | In place. A script that did run in the app's page could call the shell's commands, and through `rpc` the engine's allowed methods: Tauri gives the page its IPC whether or not `withGlobalTauri` is set, so the policy, not that setting, is what stops it. Notebook output never gets the IPC (below) |
| Notebook HTML output (pandas, Plotly, `%%html`) reaches the app or sends data out | It runs in a sandboxed frame on its own origin (`nbout:`) with its own policy that allows no fetches, no remote images, scripts or fonts, and it can't navigate itself to another site (HD-020). A content security policy doesn't cover WebRTC, so a notebook written to leak its own output could still send it out that way | Mostly in place |
| Another program on the PC calls the engine | The pipe to the shell can't be reached from outside. The integrations API (off by default) needs a tool token, answers loopback only, refuses browser requests and, on Windows, answers only programs running as your Windows account (Windows says which process holds the connection and which account runs it; anything it can't confirm is refused). It doesn't start when another account's program is listening on its port | In place. A program running as you can still decrypt the token cache (below) |
| A web page calls the local API | `Origin` refused, `Host` checked against loopback names | In place |
| A tampered or mixed-up engine download | The engine zip's SHA-256 is checked against the release's `version.json` before it is unpacked, and the unpacked engine must be the build the release names. The same holds for the engine update zip (`engine_update_sha256`), which is applied only to a copy (hard links where the disk allows) of an installed engine whose runtime key matches the release's, leaving that engine as it was; the result must name the release's build and runtime key, or the whole engine is downloaded instead | In place from FD-102a; update zip from engine_patch.rs |
| A tampered or mixed-up app update | The exe's SHA-256 is checked against `version.json` and the exe must carry its build commit. That checksum comes from the same release as the file, so it proves the download is whole, not who made it: a build that is itself signed also installs only an update signed by the same publisher (the certificate's full subject and its Trusted Signing identity usage, checked with Windows' `WinVerifyTrust`), and it installs and runs only its own engine, the one whose SHA-256 it was built with: it never takes another build's engine from the channel, so a new engine only arrives inside a signed app update. If that engine's release is gone (CI keeps the newest builds and every Stable build), the app says to download the current build. Once signing is set up, CI stops a build of main that comes out unsigned, `version.json` says `"signed": true`, and Promote to stable refuses anything else and, once reviewers are set on the `stable` environment, waits for one of them to approve. The publisher is the certificate's subject, so if KratosBI's validated identity ever changes (a new legal name or address), signed builds stop updating themselves and people install the next build by hand once | In place from FD-102a; a missing checksum is refused for both (HD-008, #158). The publisher check starts with the first signed build a PC runs; until then someone who can publish releases can still publish an update (SH-2) |
| An older build installed from an out-of-date or replayed `version.json` (a stale cache, or an old file served again) | CI and Promote stamp `version.json` with `published` (Unix time). The app remembers, per channel, the newest stamp it accepted and refuses an earlier one, an unstamped one after a stamped one, or the same stamp naming another build; the exe and engine are both checked. `update_app` installs only the build the last accepted check offered. A build older than the running one is still installed when the channel names it with a newer stamp, which is how a deliberate rollback works ([rollback](release-management/README.md#rollback)) | In place from HD-022 (SH-5). Releases published before the stamp aren't ordered, so protection starts with the first stamped `version.json` a PC sees. If `%LOCALAPPDATA%\FabricDesktop\update-state.json` is missing or corrupt, the app starts over and accepts whatever the channel shows next, so one older release can get through once; this is deliberate, so a damaged file never blocks updates. A PC clock more than 24 hours behind refuses every update ("published in the future") until the clock is fixed. Someone who can publish releases can still stamp anything (SH-2) |
| A new build that can't start leaves the PC without a working app | The running exe first ends its local engine the way quitting does, stopping any call or run still in progress rather than waiting for it (the local API port, DuckDB files, kernels and token cache are free for the new build), is kept as `kratosforge.exe.old`, and waits until the new one has opened its window and asked for the startup check (up to 90 seconds). If the new one exits before that, the previous exe is put back, starts its engine again if it was running, and keeps running; `.old` is removed only by an exe that got that far. If a call still holds the engine 10 seconds after it was ended, the update is refused and nothing is swapped | In place from HD-022 (SH-5). A new build that hangs without exiting is left running, because builds from before HD-022 (which a rollback can install) never confirm their start. Checked by unit tests on Linux; needs a manual check on Windows |
| A Stable PC getting an untested engine | The engine comes from the Stable release | In place: Stable falls back to another channel only when its release has no engine, never on a network error (HD-008, #158). With `"auto_update": false` the engine comes only from the exe's own `build-*` release (or IT's copy of it, with `engine_download_url` below) and must be the exe's build, so no newer engine is installed (#418) |
| Someone who can publish releases replaces every file | Checksums in the same release don't stop this. Code signing would (waiting on the Trusted Signing account); build provenance attestations are produced but nothing checks them yet | **Open** (SH-2, HD-021). Until signing exists, releases publish unsigned without failing |
| A `curl.exe` or `tar.exe` saved next to the app runs instead of Windows' own | Windows tools run by full path from `%SystemRoot%\System32` | In place from FD-102a |
| A `python.exe` planted earlier on `PATH` runs as the engine | The shell runs only the engine under `%LOCALAPPDATA%\FabricDesktop\engine`, or `FABRIC_DESKTOP_PYTHON` when it is a full path. Release builds never look up a bare `python` on `PATH`: a published build downloads and installs its engine before starting it, and a build with no engine to download stops with "The KratosForge engine isn't installed, and this build has none to download", naming the two ways to fix it (install a published build, or set `FABRIC_DESKTOP_PYTHON` to a full path). Only debug builds (`cargo run`) fall back to `python` on `PATH` | In place from HD-026 (SH-10) |
| A spoofed Fabric response or a proxy steers the token to another site | A next-page or operation URL from Fabric is followed only over https on the same host or a Fabric, OneLake or Power BI host; anything else is refused before a request is sent | In place (HD-058) |
| Tokens copied from the PC | On Windows the cache is encrypted with DPAPI for your Windows account, so a copy (a backup, another account, a disk read from another PC) can't be used. A plain cache from an earlier version is encrypted the first time the new build starts, without signing in again. Written atomically, and the app and scheduled runs change it one at a time under a lock, each on the file's latest contents, so a sign-out or sign-in in one isn't undone by the other; with Windows sign-in the broker holds the primary token | In place on Windows from HD-013; needs a manual check on Windows. Any program or notebook running as you, including Python an AI tool runs, can still decrypt it (EN-2): DPAPI can't tell your programs apart. On other OSes the cache is a file only you can read |
| Tokens or personal data in logs, error messages or Report a problem | `redact.py` removes tokens, keys, passwords and Teams / Office 365 webhook addresses (whole, or the path a failed post prints on its own) from every error the UI shows, the audit log and agent logs; Report a problem and support bundles also remove emails, user names in paths and ids (FD-131a, FD-138) | In place, including agent log fields (HD-007, #157) |
| Silent overwrites of OneLake data | Writes are version-checked; Save as table and CTAS refuse to replace a table unless asked (PR #51, #54); proofs write to sandboxes | In place. A retry after a post-commit failure no longer writes rows twice (HD-001, #138); `notebookutils.fs` folder deletes need `recurse=True`, refuse managed `Tables/` and honour the external-run write guard (HD-003, #154) |
| Someone on the PC loosens the organization's policy file | The file lives in `%ProgramData%`, which only administrators can change when IT pushes it ([Enterprise install](enterprise-install.md)). **Settings > Help and about** warns when the person using the PC can change it | Partly in place. The policy file stops mistakes, not someone set on getting round it: the engine is installed in the person's own profile, so they could change its code. To enforce which tenants people sign in to, use Microsoft Entra tenant restrictions or Conditional Access |
| Someone points other people's engine download at their own copy | `engine_download_url` in the policy file makes the app download its engine from IT's own folder, and that folder supplies both the engine and the checksum it is checked against, so the folder is trusted exactly as much as the policy file. The app uses it only with `"auto_update": false`, reads it only from `policy.json` itself (never the per-user last good copy), and only when that file and its folder are owned by SYSTEM or Administrators and grant no one else a right that could change or replace the file; otherwise the engine comes from GitHub and **Settings > Help and about** says why. So a standard user who creates `%ProgramData%\FabricDesktop` on a PC with no IT policy can't name a folder for the next person. Builds from CI also carry the checksums of their own engine files inside the exe, so even a trusted folder can only serve the exact engine the exe was built with | In place; checked by unit tests, not yet on Windows |
| Tests writing to production | The [live test](https://github.com/KratosDataGod/KratosForge/blob/main/docs/live-testing.md) refuses unmarked workspaces, production-looking names and Platform workspaces | In place from FD-101 |
| Secrets in project or agent files | Config validators refuse secret-looking fields; secrets come from Key Vault or environment variables | In place |
| A link or redirect takes the Fabric view, which holds your Fabric sign-in, to a page that isn't Microsoft's | The view opens pages and pop-ups only on `https` with no user name in the link and no port, on exactly these hosts: `app.fabric.microsoft.com` (the Fabric portal), `app.powerbi.com` (Fabric's former portal; older item links redirect through it), `login.microsoftonline.com` and `login.microsoft.com` (Entra ID sign-in and sign-out), `login.windows.net` (Entra ID's legacy sign-in host, still used by older links and some redirects), `device.login.microsoftonline.com` (the device step where Conditional Access checks the PC), `autologon.microsoftazuread-sso.com` (Seamless SSO on domain-joined PCs) and `login.live.com` (a guest signing in with a personal Microsoft account). Other web links open in the default browser; plain `http` to those hosts and other schemes are refused. An allowed pop-up (a sign-in window) opens in a window the app builds with the same filter, so it can't leave those hosts either, and it keeps `window.opener` so sign-in can report back to the page that opened it. If that window can't be built, the pop-up is refused: it never gets WebView2's own window, which has no filter. The Monitoring hub's pop-out window (Preview) has a Fabric view of its own on the same profile, built with the same filter and pop-up rule; the app's own page in a pop-out window opens only the app's pages, with web links going to the default browser. Microsoft Defender SmartScreen stays on in the view (SH-12, HD-027) | In place. A tenant whose sign-in hands off to its own identity provider (AD FS, Okta, Ping and similar): IT adds that provider's host with `fabric_view_sign_in_hosts` in the policy file ([the key](azure-setup.md#4-push-settings-to-everyone)), and those hosts follow the same rule. Only the policy file can add hosts. Pages that aren't part of signing in, such as registering for MFA ("More information required") or managing a personal Microsoft account, are expected to open in the default browser; sign in in the view again afterwards |
| The Power BI token Embed Studio hands its embed frame (Preview, not on screen yet) is used for something else | `pbi_embed_token` only reads, but the token is your Power BI access token: it can do anything you can do in Power BI with KratosForge's Power BI permissions, write permissions included, so it is the first token that can write to reach the app's own page. The app keeps it in memory only (never local or session storage, snapshots, error reports or logs), hands it only to the embed host, which frames `app.powerbi.com` and nothing else, and asks the engine for a fresh one before it expires (about an hour) instead of keeping one. External AI tools can't ask for it ([Power BI embedding](architecture/power-bi-embedding.md)) | Engine calls in place (PBE-04); the screen (PBE-06) follows these rules |
| Command injection through schedules | Task Scheduler is called with argument lists, never a shell; XML values are escaped | In place |

## Content Security Policy

The main window's policy is set in `app/src-tauri/tauri.conf.json` (`app.security.csp`):

```
default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self' data:;
connect-src ipc: http://ipc.localhost; frame-src nbout: http://nbout.localhost https://nbout.localhost
  pbiembed: http://pbiembed.localhost https://pbiembed.localhost;
object-src 'none'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'
```

- **Scripts:** only the files in `app/ui/`. No inline scripts or handlers, no `eval`. A UI test fails if the policy is missing, allows `'unsafe-eval'`, or allows inline or remote scripts.
- **Styles:** `styles.css`, plus the code editor's `<style>` element, which carries the nonce Tauri adds to `style-src` on each load. Inline style attributes aren't allowed; the UI sets styles through the DOM (`element.style`), which the policy doesn't restrict. No `'unsafe-inline'`.
- **Images:** the app's own files and `data:` (notebook charts). Nothing is loaded from the internet.
- **Connections:** only the shell (Tauri's IPC). The UI never calls the engine's local HTTP API or any web address; the engine makes every network call.
- **Frames:** only notebook HTML output and the Power BI embed host (below), both served by the shell. No remote site. The Fabric view (Monitoring hub, OneLake catalog, Fabric's sign-in) is a separate webview, not a frame, so this policy doesn't apply to it; app sign-in runs in the engine, through Windows sign-in or the system browser.

Notebook HTML output comes from whoever wrote the notebook, so it never runs in the app's origin. The shell serves a small frame page from its `nbout:` scheme (`http://nbout.localhost` on Windows), for the main window only. The page loads it in an `<iframe sandbox="allow-scripts">` without `allow-same-origin`, posts it the HTML, and the frame writes the HTML into itself. The frame keeps its own policy: inline scripts and styles (and `eval`, which some charting libraries use) are allowed, because the output needs them and can reach nothing; images and media only as `data:` or `blob:`, fonts only as `data:`; `default-src 'none'`, so no fetches, beacons or remote resources. A content security policy doesn't cover WebRTC, so script in a notebook written to leak data could still send it out through a WebRTC connection; treat a notebook from someone you don't trust like a script you were sent. Its origin is opaque and it never receives the shell's invoke key, so it can't call the Tauri API, and the main window's `frame-src` stops it from navigating itself to another site. HTML output that loads its scripts from the internet (Plotly with `include_plotlyjs="cdn"`, for example) shows nothing; the engine's own Plotly output inlines plotly.js. Altair charts reach the frame as their Vega-Lite spec, written into the frame's script with every `<` escaped, together with the Vega libraries the app ships (`app/ui/vendor/vega`), so they draw there and never run in the app's page.

The Power BI embed host (Embed Studio, Preview, not on screen yet: PBE-03 in [Power BI embedding](architecture/power-bi-embedding.md)) is a second frame page the shell serves, from its `pbiembed:` scheme (`http://pbiembed.localhost` on Windows), for the main window only. It holds Microsoft's `powerbi-client` SDK (vendored in `app/src-tauri/embed-host/vendor`, checked against the npm tarball's hash by a test) and has its own policy:

```
default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self' data:;
frame-src https://app.powerbi.com; connect-src 'none'; base-uri 'none'; form-action 'none'; object-src 'none';
frame-ancestors http://tauri.localhost https://tauri.localhost tauri://localhost
```

- It frames `https://app.powerbi.com` and nothing else, and fetches nothing. The SDK posts the person's token to its frame with target origin `*`, so `frame-src` is what keeps that frame, and the token, on Power BI. The host also refuses an embed address on any other host before the SDK sees it.
- Only the app's own window can frame it (`frame-ancestors`), and the shell serves its files to no other webview.
- It acts only on a fixed list of commands (embed, new token, pages, change page, reload, full screen, reset), only from its parent window on one of the app's origins, and answers only that origin. Messages from Power BI's frame, or anything else, are ignored.
- Events go back to the app with every key that looks like a token or secret removed. Text inside other values (an error's message, say) is passed as Power BI wrote it.
- The token comes from the engine (`pbi_embed_token`, PBE-04) and lives only in memory: the app's window, the host frame and Power BI's frame. It is never written to disk or a log.
- Its origin isn't the app's, so the Tauri API refuses it like any remote page.
- Only the commercial cloud's `app.powerbi.com` is allowed. Power BI in government and sovereign clouds (such as `app.powerbigov.us` or `app.powerbi.cn`) won't open in the host.
- Pop-ups from the frame open nothing (checked in WebView2 156, PBE-01). Opening Power BI's links in the default browser comes with the screen.

## Data copied to this PC

Running on this PC means reading OneLake data into the PC: previews, notebook DataFrames, SQL results, local tables and exports. Fabric's own protections are checked when the data is read, and stop applying once it is here.

| In Fabric | On this PC |
| --- | --- |
| OneLake data access roles decide which folders and tables a person can read | Checked once, when the app reads with your token. A copy on the PC has no roles: anyone or any program that can read your files can read it |
| Row-level and column-level security (RLS, OLS) on a SQL analytics endpoint, Warehouse or semantic model filter what a query returns | Not applied. Notebooks and SQL on this PC read the Delta files in OneLake directly, the way Spark does, so they see every row and column your OneLake access allows |
| Sensitivity labels and Purview policies stay attached to the item | Not carried onto local files or exports |
| Data stays in the tenant's region and under its retention rules | Cached copies (previews, staged tables, download cache, table and column names for completion) are deleted after the `local_retention_days` policy (default 30 days, [Azure setup](azure-setup.md)). Local tables, notebook outputs and exports stay until someone deletes them. The tenant's retention rules don't reach them |
| OneLake diagnostics can log who read what | The read is logged there like any other. What happens to the copy afterward is in the app's own audit log at most |

What this means in practice:

- Give people OneLake access only to the data they may hold on their PC. If a table must only ever be seen through RLS, keep it out of lakehouses those people can read directly, and query it through the SQL endpoint or the semantic model in Fabric instead.
- The PC is the protection: BitLocker, a managed device and a per-user profile. KratosForge keeps local data under `%LOCALAPPDATA%\FabricDesktop` and project folders and doesn't encrypt it itself.
- Running a notebook in Fabric (**Runs on: Fabric**) keeps the data in the tenant.

## Personal data in the platform's catalog

The platform's catalog (SQL_Platform, or the SQLite file on this PC) is readable by everyone with Viewer on the Platform workspace. Besides names in owner fields, it holds:

| What | Where | When |
| --- | --- | --- |
| Who made each change, and when | `catalog.audit` | Always: every platform change |
| The date each person last used the platform | `catalog.person` (user name, last-used time) | Only when the policy file sets `platform_presence` to `true`. Off by default |
| Who follows which data product | `catalog.follow` (user name, product, when) | When someone presses **Follow** ([Follow a product](data-mesh.md#follow-a-product-preview)). The app lists a product's followers only to its owners and platform admins; anyone with direct read access to the catalog's tables can still see them |
| Business keys and the surrogate keys issued for them | Each key table (`keys.<name>`) in `SQL_Keys` in the Keys workspace (in `SQL_Platform` until keys move there) | Readable by everyone with Viewer on the Keys workspace and Execute on UDF_Keys (`lookup_key`, `export_keys`), in full, whatever their role on the platform. A business key can be personal data, such as an email or a customer number: where it is, use a non-personal source id as the business key, or keep that key table in a workspace only its readers can see |

`platform_presence` feeds owner coverage's check that an owner hasn't gone quiet ([Platform > Owners](platform.md#owners-preview)). It is per-PC policy: a PC without it writes nothing, and its Owners card doesn't check quietness at all. Turn it on only where your works council and privacy notice cover it. Turning it off later stops new writes; existing rows stay until a platform admin deletes them from `catalog.person`.

## Supply chain

- Python packages are pinned exactly in `sidecar/constraints.txt` and CI installs with it; Rust builds use `Cargo.lock` with `--locked`.
- CI publishes SHA-256 checksums in `version.json`, which the app now enforces.
- In place (FD-103): `pip-audit` and `cargo audit` on every pull request, CycloneDX SBOMs for the shell and the engine, build provenance attestations on releases, third-party actions in `ci.yml` pinned by commit SHA, and signing that runs only for pushes to `main`.
- Every workflow pins its actions by commit, and only the docs deploy job on `main` can publish Pages (SH-8).
- The Windows agent installer and `install-sidecar` install the exact versions in `sidecar/constraints.txt` (SH-9).
