## Outcome

**Accepted with Documented Limitations** (recommended).

The CSP is set, the UI and CSP tests pass, and they fail when the CSP is removed. Notebook HTML output runs in a sandboxed frame with an opaque origin and its own policy with no `connect-src`. A probe in Chromium found it can't reach the parent page, the IPC endpoint or the network. Two things are open. The WebView2 part is only checked by reading the code. And docs/security.md says the frame "never receives the shell's invoke key", but the Tauri source this build uses puts the invoke key in every frame on Windows (finding 1). The boundary still holds, but on other layers than the one the docs name.

## Findings

| # | Severity (blocking / should fix / note) | Finding | Where | Status |
| ---: | --- | --- | --- | --- |
| 1 | should fix | security.md says the output frame "never receives the shell's invoke key, so it can't call the Tauri API". Tauri 2.12.2 marks its IPC and invoke key scripts `for_main_frame_only`, but wry 0.57 says that on Windows "scripts are always added to subframes regardless of the `for_main_frame_only` option" (wry lib.rs:1029, webview2/mod.rs:506-508, `AddScriptToExecuteOnDocumentCreated`). So on WebView2 the frame probably has `__TAURI_INTERNALS__` and the key. What actually stops it is the opaque origin, the frame policy with no `connect-src` (guarded by the Rust test) and WebView2's per-frame message routing. The docs should say that. | docs/security.md "Content Security Policy" section | Open: docs owner |
| 2 | should fix | No committed test renders `type: "html"` output and checks that it can't reach the parent or the IPC endpoint. The ui.test only matches the `htmlFrame` source text; the Altair and Plotly tests only check that nothing is fetched. A test like the reviewer probe would catch an `allow-same-origin`, a `connect-src` added to the frame policy, or a new listener in the app page. | app/tests/browser | Open |
| 3 | should fix | On Windows (WebView2), nobody here checked that script in the output frame can't call `invoke`: the frame does get Tauri's scripts, and `nbout.localhost` counts as a local origin, so the defence rests on WebView2's frame handling. A short check: a `%%html` cell with `<script>__TAURI_INTERNALS__.invoke("check_components").then(r=>document.body.textContent="REACHED", e=>document.body.textContent="refused "+e)</script>`, which should not show REACHED. | Windows build | Open: Chris, FEAT-SEC-02 next action |
| 4 | note | `withGlobalTauri: true` stays, so anything that did run in the app's page could call the API. The CSP (`script-src 'self'`) and escaping are the layers in front of it, as security.md:35 says. Notebook Markdown is still rendered with `innerHTML` in the app's page (app.js:2580), under that CSP. | tauri.conf.json:9 | Known; outside this item |
